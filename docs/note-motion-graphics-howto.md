# note記事素材｜AIでモーショングラフィックを作って、動画ファイルにする方法

> **この資料の位置づけ**: noteで「モーショングラフィックの作り方」を公開するための素材（事実・手順・コツ・コード）。
> 記事化（構成・文体・タイトル・タグ・画像プロンプト）は、受け取った側（天才会議）で note365 のルールに沿って行う。
> ここに書いたことは、実際に作った作品（hihaho 2026年9月リリースノートの解説動画）で試して確認した内容。未確認のことは「未確認」と明記した。

## 0. 結論（TL;DR）

- AIは動画ファイルを直接つくらない。**「1コマを描くコード」を書かせて、1コマずつ撮影し、動画につなぐ**のが定番。
- 道具は3つだけ。**HTML（Canvas）／ Playwright（ヘッドレスブラウザ）／ ffmpeg**。
- 絵はすべて「時間 t の関数 `seek(t)`」にする。これで何度書き出しても同じ映像になり、途中の1コマだけ確認することもできる。
- **見栄えより「理解しやすさ」を優先**すると仕上がりが一気によくなる。文字を大きく、1行を短く、1行ずつ出す。
- 音（BGM・効果音）も**コードで合成**できる。映像と同じ「拍」で設計すると、ズレずに合う。
- 最後に `ffmpeg` で映像と音を合わせて MP4 にする。

---

## 1. 仕組み（全体像）

```
index.html（seek(t) で1コマを描く）
   ↓ Playwright が t を進めながら1コマずつスクリーンショット（PNG連番）
   ↓ audio.py が BGM と効果音を WAV に合成
   ↓ ffmpeg が 連番画像 + 音声 を MP4（H.264 + AAC）にまとめる
hihaho-release-sep-ja.mp4
```

なぜこうするのか:
- ブラウザの `requestAnimationFrame` や CSS アニメーションは「実時間」で動くため、1コマずつ撮ると**タイミングがずれる**。
- そこで **時間を自分で渡す**（`seek(t)`）。`Date.now()`・タイマー・CSS transition は使わない。
- Opus 5.5 でのモーショングラフィック事例でも、同じ方式（`draw(t)` / `seek(t)` を書かせ、ヘッドレスブラウザで全コマを撮り、ffmpeg で連結）が広く紹介されている（出典は末尾）。

## 2. 手順（再現できる形）

### ステップ1｜先に「絵コンテ」を作らせる
いきなり作らせず、まず次を決める。
- 目的・見る人・長さ・画角（今回は 1920×1080、129秒）
- ショットごとの **開始時刻／画面の動き／文字／つなぎ**

プロンプト例:
```
hihahoの9月リリースノートを、見る人が内容を理解できる解説動画にしたい。
まず絵コンテを出して。ショットごとに「開始時刻・文字・動き・次への繋ぎ」を表にして。
長さは3分以内。見栄えより理解しやすさを優先。
```

### ステップ2｜時間を「拍」で決める
BPM120にすると **1拍＝0.5秒**。演出を秒ではなく拍番号で書く。音楽と効果音を後から合わせやすくなる。
（今回は 258拍 = 129秒。イントロ12拍／全体像10拍／ハイライト5本×44拍／まとめ16拍）

### ステップ3｜1ファイルのHTMLを書かせる
プロンプト例:
```
Canvas で 1920x1080 の動画を描く index.html を1ファイルで作って。
- window.DURATION（秒）と window.seek(t) を公開。seek(t) は時間 t の1コマを描く純粋関数
- Date.now / requestAnimationFrame / CSS transition は使わない
- 演出は拍番号で書く（BPM120、1拍 = 0.5秒）
- 色・フォントは先に決めたものだけ使う（ロゴ画像は同じフォルダ）
```

骨組み（実際に使った形）:
```js
window.DURATION = 129;                      // 秒
const BEAT = 0.5;                           // BPM120
window.seek = function (t) {                // t 秒の1コマを描く
  const b = t / BEAT;                       // 拍番号
  if (b < 12) intro(b);                     // 拍で場面を切り替える
  else if (b < 22) agenda(b - 12);
  else chapters(b);
};
```

### ステップ4｜代表フレームだけ確認する
全コマを書き出す前に、**章ごとに数枚だけ**撮って並べて見る。文字の見切れ・重なり・空白フレームをここで潰す。
（今回は18枚を1枚の一覧画像にして確認。書き出しは確認が済んでから）

### ステップ5｜撮影する（Playwright）
```python
from playwright.sync_api import sync_playwright
import pathlib

FPS = 30
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 1920, "height": 1080})
    page.goto(pathlib.Path("index.html").resolve().as_uri())
    page.evaluate("window.READY")                 # ロゴ画像・フォントの読み込み待ち
    total = int(page.evaluate("window.DURATION") * FPS)
    for i in range(total):
        page.evaluate(f"window.seek({i / FPS})")   # i コマ目の時刻を渡す
        page.locator("canvas").screenshot(path=f"frames/{i:05d}.png")
    browser.close()
```

### ステップ6｜動画にする（ffmpeg）
音声なし:
```bash
ffmpeg -y -framerate 30 -i frames/%05d.png \
  -c:v libx264 -pix_fmt yuv420p -crf 18 out.mp4
```
音声あり（BGM・効果音のWAVを合わせる）:
```bash
ffmpeg -y -framerate 30 -i frames/%05d.png -i audio.wav \
  -c:v libx264 -pix_fmt yuv420p -crf 18 \
  -af "loudnorm=I=-17:TP=-3:LRA=11" -c:a aac -b:a 160k -shortest out.mp4
```
ポイント:
- **`-pix_fmt yuv420p` は必須**（入れないと QuickTime やSNSで再生できないことがある）。
- `-crf` は小さいほど高画質（18は十分きれい）。
- `loudnorm` で音量を揃える（-17 LUFS、ピーク -3dB）。

## 3. 「見やすく・理解しやすく」するコツ（実体験）

最初に作った版は「見栄えは良いが、内容が頭に入りにくい」状態だった。次の直しで一気に分かりやすくなった。

| 直したこと | 前 → 後 | 効いた理由 |
|---|---|---|
| 説明文の文字サイズ | 約38px → **54px** | スマホ・小さい画面でも読める |
| 1行の長さ | 長文 → **16文字以内** | 一目で意味が取れる |
| 表示のしかた | 3行を同時 → **1行ずつ出す。次が出たら前を薄く** | 今読むところに目が行く |
| 最初に全体像 | なし → **「今回の5つ」を一覧で先に見せる** | これから何を見るか分かる |
| 図解の大きさ | 小さい → **1.25倍に拡大** | 何が起きているか見える |
| 図解と説明の同期 | バラバラ → **説明の行と図の動きを合わせる** | 言葉と絵が結びつく |
| 動きの速さ | そのまま → **約半分の速さ** | 読む時間が確保できる |
| 1テーマの長さ | 14秒 → **22秒** | 読み終える前に切り替わらない |
| 進行表示 | なし → **章番号（01/05）と進行バー、章ごとの色** | 今どこかが分かる |

そのほかの小さなコツ:
- 色は章ごとに1色（ロゴの色から取る）。文字は常に濃紺（コントラスト確保）。
- 「ボタン」「質問」などの**図の中の小さな注釈**も大きくする（意外と見落とす）。
- 「かっこよく」ではなく「**文字を54px、1行16字以内**」のように**数字で**指示する。

## 4. 音のつけ方（BGMと効果音をコードで合成）

外部の音源は使わず、Python（numpy）だけで作った。理由は、**映像の拍と完全に合わせられる**こと、素材の権利を気にしなくてよいこと。

- **BGM**: C–G–Am–F のコード進行をループ。イントロはパッドだけ、本編でアルペジオとベース、全体像以降でハイハットとキックを足す。
- **効果音（約126か所）**: 映像側の `window.SFX()` が「何拍目にどの音か」を出力し、`audio.py` がそれを読んで合成する。**映像と音のタイミングの元が同じ**なのでズレない。

| 場面 | 効果音 |
|---|---|
| 画面転換 | スイープ（ノイズを上げて下げる） |
| 章扉の数字が着地 | 低い「ドン」 |
| 説明の行が出る | 短い2音の「ピッ」 |
| 図解が出る | 音程が上がる「ぽん」 |
| キーを押す | 低めの「カチッ」 |
| 成功 | ベルの「チーン」 |
| 到達できない／注意 | 下がる2音 |
| タイマーの残りわずか | 高い「ピッピッ」 |
| ロゴ登場 | 4音のアルペジオ |

効果音の例（ぽん）:
```python
def sfx_pop(v):
    t = tvec(0.14)
    f = 520 + 520 * (1 - np.exp(-t / 0.025))     # 音程が上がる
    y = np.sin(2 * np.pi * np.cumsum(f) / SR) * np.exp(-t / 0.05)
    return y * 0.5 * v
```
- 音量は BGM を小さく、効果音を目立たせる。最後に `loudnorm` で全体を揃える。
- **未確認**: 実際に耳で聞いたバランスの評価は、制作者側ではしていない（数値上は問題なし）。記事化の前に、実際に再生して確認してもらう。

## 5. 動画ファイルへの書き出し（まとめ）

### 方式A｜HTML + Playwright + ffmpeg（今回の方式）
- メリット: 依存が少ない。1ファイルで完結。音も自由に作れる。
- デメリット: 書き出しスクリプトを自分で用意する。

### 方式B｜Remotion（React）
```bash
npx remotion render MyVideo out/video.mp4
```
- 主なオプション: `--codec=h264`（Web向け）／`--codec=prores-4444`（透過付き高画質）／`--crf=18`／`--scale=2`
- メリット: プレビューがすぐ反映される。書き出しが1コマンド。
- デメリット: Node/React の環境が必要。構成が重め。

### 書き出し時間の目安（今回の実測）
- 129秒・30fps・1920×1080 = **約3,900コマ**。4コアのサーバーで**約5〜6分**（日本語版と英語版を並行して書き出し）。
- フレームレートを60にすると、およそ2倍かかる。

## 6. つまずいたところと対処（実際に起きたこと）

| 症状 | 原因 | 対処 |
|---|---|---|
| Playwright が起動しない | 入っているブラウザのバージョンが合わない | `executable_path` で既存の Chromium を指定 |
| 日本語が細い・太字が出ない | サーバーに日本語の太字フォントがない | `fonts-noto-cjk` を入れる。Mac なら不要 |
| 音が大きすぎて歪む | ピークが 0dB に達した | `loudnorm` のピークを -3dB に。さらに必要なら音量を下げて再エンコード |
| 外部サイトの情報が取れない | AIの実行環境のネットワークが制限されている | 許可ドメインを設定（**変更は新しいセッションから有効**） |
| 同じブランチに別作業が混ざる | 複数セッションが同じブランチへ push | 先に取り込んでから push（強制 push はしない） |
| 説明と図の動きがずれる | 時間を別々に管理していた | 図解の時間を1つの関数（`warp`）でまとめて遅くする |
